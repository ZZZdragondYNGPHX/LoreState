# 0.9.0 模块条目与试卡

0.9.0 试用版，组件交付，Git 固定标签 `prototype-v0.9.0`。人物、物品、国家和作者自定义类别可以各有自己的栏目与更新规则。每轮仍只调用原有剧情模型一次，在正文末尾输出一个 LoreState 更新块，脚本校验后整轮提交。

按新配置和新聊天使用，不提供旧数据、旧条目或旧配置迁移。新建配置和生成 HTML 制作提示词时必须提供模块格式。真实酒馆、实际模型和游玩效果尚未验收。

## 直接试用

1. 在独立测试角色卡、新聊天中使用 [main 远程组件](../prototype/dist/main/lorestate-script.json)，或在酒馆助手脚本中导入 `@main` 的远程 bundle。刷新脚本即可取得最新开发版；固定 `prototype-v0.9.2` 入口只代表历史稳定代码。CDN 可用性需独立验证。
2. 将 [完整模块条目示例](../prototype/module-example.txt) 放进一个世界书条目，绑定到测试卡。避免同时通过世界书常驻激活再次发送整个条目；由脚本统一组装状态提示。
3. 在 LoreState 设置里选择该条目，粘贴 [配套 HTML](../prototype/module-example.html)，预览后保存并启用。预览会分别展示人物、物品、国家、事件示例。
4. 可使用现有“作者初始档案”功能提供明确初值；不提供时由首轮正文建立 full 状态。
5. 用“查看下一轮状态提示”检查实际会发出的模块目录、详细规则和档案。本按钮不会调用模型。

这两个示例可以直接配套使用。自行制作 HTML 时，继续使用“生成并复制 HTML 制作提示词”。

## 条目格式

```text
【LoreState模块 v1】
【通用规则】
只记录正文已经确认的持久事实；猜测不写成事实。
【公共栏目】
栏目：地点、时间
明确移动或时间推进时更新。
【模块：人物】
栏目：身体状况、当前目标
受伤或恢复时更新身体状况；明确改变意图时更新当前目标。
【模块：物品】
栏目：持有者、完好状况
交付、拾取或遗失时更新持有者；损坏或修复时更新完好状况。
```

第一行是格式版本。标题单独占一行，不缩进、不加 Markdown 标记。每个公共或模块分区的首个非空行必须是 `栏目：`，栏目之间使用中文顿号 `、`；其后都是该分区的自然语言规则。通用规则、公共栏目可以省略，模块需要 1–16 个，不得重名。暂不支持分区嵌套。

模块名和栏目名使用文字或下划线开头，后续可用文字、数字、下划线、连字符，最多 40 字符。公共栏目最多 32 个；当前版本全部实体模块合计最多 32 个不同栏目名，每个模块至少一个。同名栏目可以出现在不同模块，值存于各自实体中。条目最多 24000 字符；实际组装后的规则和档案总预算也是 24000 字符，超限会中止生成。

栏目定义来自条目。HTML 必须完整展示声明的栏目，不能借换肤增删字段或改变模块归属。结构改变需要新配置和新聊天；单独调整规则文字可以在后续生成时生效，不会重算历史语义。

字段约束继续配置于 `shared` 和 `entity`。`entity` 中某字段的必填、禁止删除和枚举约束只作用于含有该字段的类别；不同模块若使用同名字段，会共用这条约束，暂不支持同名字段按类别配置不同枚举。

## 每轮加载什么

- 通用规则、公共栏目规则、全部模块的名称与栏目目录始终提供。
- 首次建立状态时提供所有模块详细规则，便于正确初始化。
- 已有状态时，当前热档、活动事件、明确提及的实体及一跳关联完整档案，会带上其所属模块的详细规则。用户直接写出模块名称也可触发该类规则。
- 冷档索引本身不触发详细规则，也不代表已经读取旧档。预算撤下可选完整档案时，同时重新计算所需规则和读取权限。
- 正文意外出现一个已声明但未选中的类别，可以按常驻目录和通用规则建立新档，只记明确事实，未知填“未知”；新实体成为热档后，下一轮会加载该类详细规则。需要建档当轮就生效的限制，应写入通用规则或机器字段约束。

例如热档只有人物、物品时，国家栏目目录仍在，但整段国家更新规则不会每轮发送。这里没有语义检索、代词理解、别名自动识别或额外模型调用。规则是否省空间取决于本轮涉及的类别，不能保证每轮都缩短。

没有声明“事件”模块时，不会要求 AI 建立事件实体。需要承诺、倒计时等持续活动事件的卡，应显式声明事件模块。

## 更新和展示

继续使用 `version="3"` 的 Shared / Entity 外层协议。实体的 `type` 必须匹配已声明模块；新实体 full 只填写自己模块的全部栏目，已存在实体 delta 只写变化，遗漏保留。多个类别的更新放在同一个 LoreState 块中，任何非法栏目或无效读取都会拒绝整轮提交。

人物交还钥匙的已确认变化可以写成：

```xml
<LoreState version="3" mode="delta">
  <Entity id="P1" mode="delta"><当前目标>返回书店</当前目标></Entity>
  <Entity id="I1" mode="delta"><持有者>守卫</持有者></Entity>
</LoreState>
```

示例假设 P1、I1 已建立且可更新；真实生成必须复制当轮提示提供的 read 凭据。脚本验证结构、栏目和提交完整性，不能仅靠程序保证 AI 对正文含义的理解正确。

HTML 保持一个 `data-lore-entity` 重复容器。在其中用 `data-lore-module="人物"` 等分区包住分类栏目，脚本只保留当前实体所属类别的分区。分区不可嵌套，不能同时充当字段绑定节点。跨类别共有栏目可放在分区外；它必须属于所有已声明模块。冷档详情也只列所属模块的栏目。

## 真实试卡清单

| 情境 | 应观察到的结果 |
| --- | --- |
| 新聊天首次生成 | 初轮详细规则齐全；只填写已建立类别的全部栏目 |
| 纯人物对话，其他类别转冷且无关联 | 下一轮没有其他类别详细规则，公共状态和目录仍在 |
| 人物交付物品 | 正文与两个实体的更新一致，未变化字段保留 |
| 正文发现新物品 | 按目录创建物品档案；下一轮带上物品规则 |
| 提到冷档的唯一名称或编号 | 完整取回及其规则出现；有效 read 允许本轮更新 |
| 未读取冷档却直接改字段 | 整轮拒绝，原状态不变 |
| 国家实体输出人物专用字段 | 报错，不保存半份更新 |
| 修改模块栏目后继续生成 | 请求前中止，要求新配置和新聊天 |
| 重抽、删尾、刷新、回档 | 记录按当前分支回放，分类栏目与读取凭据保持一致 |
| 窄屏状态栏 | 各实体只显示本类栏目，没有错误的空白类目 |

自动证据见 [验证记录](../prototype/verification.md)。`realHostVerified=false`，未设置 `driver-accepted`。下一关是用户在真实酒馆中统一试卡；本次 Git 分发已获用户授权；真实安装和最终游玩验收仍待完成。
