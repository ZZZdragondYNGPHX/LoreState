# 可复制条目与连续更新示例

适用 0.7.0 / v3。`text` 代码块是可粘贴进世界书的规则正文；`xml` 代码块是模型应输出的状态示范，不要把整套示范当作每轮固定输出。

## 示例一：只有地点与时间

适合先验证最小流程。模板只需两个公共字段，没有实体容器。

```text
【记录目标】
维护当前场景的地点与时间，为后续叙事提供连续依据。

【公共栏目】
地点：记录玩家当前所在的具体场所。明确移动到新地点时更新；只谈到其他地点不改变当前位置。
时间：记录故事内已经确认的日期或相对时段。只有正文明确推进时间才更新；无法判断具体钟点时使用“当日下午”等已有依据的描述。

【初始状态】
地点为河港书店，时间为第三天清晨。

【维护规则】
每轮核对这两项，只在事实变化时更新。不推算没有依据的日期，不为换一种说法而重写。
使用 LoreState 提供的状态协议，正文继续正常叙事。
```

首次记录：

```xml
<LoreState version="3" mode="full">
  <Shared><地点>河港书店</地点><时间>第三天清晨</时间></Shared>
</LoreState>
```

走到码头，时间没有明确变化：

```xml
<LoreState version="3" mode="delta">
  <Shared><地点>河港码头</地点></Shared>
</LoreState>
```

下一轮只是交谈，没有状态变化：

```xml
<LoreState version="3" mode="delta"></LoreState>
```

## 示例二：旅行中的人物、国家、物品与承诺

使用 [完整配套模板](HTML模板适配指南.md)。公共栏目为“地点、时间”，所有实体共用“概况、当前状态”。以下条目可整段复制，再替换其中的故事设定。

```text
【记录目标】
保存旅途中已经确认、仍会影响后续剧情的世界状态。国家、人物、物品和未完成事件使用独立实体。

【公共栏目】
地点：玩家当前所在场所；实际移动才更新。
时间：故事内确认的日期与时段；明确推进才更新。

【所有实体共用的栏目】
概况：这个对象是谁或是什么，以及已确认的稳定事实。身份和事实真正改变时才调整。
当前状态：目前所在、持有、伤势、影响或行动进展。一次更新须写出完整的新文字，保留仍成立的其他事实。
不适用的事项不强行填写；未知信息写“尚未确认”。不要把推测写成事实。

【初始状态】
地点：河港书店；时间：第三天清晨。
N01 北境公国，类别国家，识别信息“北方公国”：与南方停战；边境仍戒备。当前剧情未涉及，初始为冷档。
P01 林舟，类别人物，识别信息“河港书商”：经营书店；正在备货，保管仓库钥匙。初始热档。
I01 仓库钥匙，类别物品，识别信息“西仓黄铜钥匙”：可打开西仓；由林舟保管，完好。初始冷档。
E01 十本书订单，类别事件，识别信息“林舟向旅人的交付约定”：第四天中午交付十本书；尚未交付，pending 为 true，保持热档。
林舟的 links 指向 I01；订单的 links 指向 P01。
以上事实最后确认于第三天清晨；北境公国的情况只确认到第二天。

【编号与更新】
沿用上述稳定编号。新对象按 P人物、N国家、I物品、O组织、L地点、E事件分配尚未使用的编号。
称号和物品持有者变化写入栏目，不修改编号、名称、识别信息或类别。
交付物品时同步更新相关人物与物品，避免两份记录互相矛盾。
只记录正文和既定初始状态确认的事实；离场期间发生了什么，没有证据就保持未知。

【冷热与召回】
暂时无关的对象转冷，保留完整资料。保留与当前行为有关的有向 links，不把全部关系网放入 links。
冷档取回不等于变成热档。需要修改冷档栏目时先空 delta 唤醒，下一轮读取资料后再更新。

【活动事件】
每轮结合公共时间核对订单。到了期限也不能默认交付；正文确认交付才将当前状态改为完成，并设 pending 为 false，之后可以转冷。
新的欠款、承诺或持续影响独立建事件，记录触发条件、进展和完成证据。未完成事件保持热档，即使参与者已经离场。

【输出】
正常写正文，末尾使用 LoreState 提供的唯一状态更新块。不输出 HTML，不另建状态协议；没有变化就输出空 delta。
```

### 第一轮：建立完整状态

```xml
<LoreState version="3" mode="full">
  <Shared><地点>河港书店</地点><时间>第三天清晨</时间></Shared>
  <Entity id="N01" type="国家" name="北境公国" identity="北方公国" mode="full" presence="cold" confirmed="第二天">
    <概况>与南方停战</概况><当前状态>边境仍戒备</当前状态>
  </Entity>
  <Entity id="P01" type="人物" name="林舟" identity="河港书商" mode="full" links="I01" confirmed="第三天清晨">
    <概况>经营河港书店</概况><当前状态>正在备货，保管仓库钥匙</当前状态>
  </Entity>
  <Entity id="I01" type="物品" name="仓库钥匙" identity="西仓黄铜钥匙" mode="full" presence="cold" confirmed="第三天清晨">
    <概况>可以打开西仓</概况><当前状态>由林舟保管，完好</当前状态>
  </Entity>
  <Entity id="E01" type="事件" name="十本书订单" identity="林舟向旅人的交付约定" mode="full" pending="true" links="P01" confirmed="第三天清晨">
    <概况>林舟承诺交付十本书</概况><当前状态>第四天中午交付，尚未交付</当前状态>
  </Entity>
</LoreState>
```

同轮允许关联稍后才声明的 I01，因为整轮会一起校验。不能关联从未建档的编号。

### 第二轮：离开书店

玩家去了码头，林舟转冷。订单仍活动，通过 E01 → P01 可以召回林舟；不会继续递归到 I01。冷档不代表有关联时也绝不加载。

```xml
<LoreState version="3" mode="delta">
  <Shared><地点>河港码头</地点></Shared>
  <Entity id="P01" mode="delta" presence="cold"/>
</LoreState>
```

### 第三轮：准备了解北境近况

玩家明确提到“北境公国”，脚本可以预取 N01；预取本身不改变冷档状态。若后面需要更新它，本轮先唤醒，不写栏目。

```xml
<LoreState version="3" mode="delta">
  <Entity id="N01" mode="delta" presence="active"/>
</LoreState>
```

### 第四轮：确认新事实

正文确认使者带来了停战延期的正式文书。现在可以更新已经唤醒的国家，并保留边境仍戒备这一事实。

```xml
<LoreState version="3" mode="delta">
  <Shared><时间>第三天下午</时间></Shared>
  <Entity id="N01" mode="delta" confirmed="第三天下午">
    <当前状态>停战延期七日，边境仍戒备</当前状态>
  </Entity>
</LoreState>
```

### 第五轮：事件完成

正文确认十本书已经送达。订单可结束并转冷。林舟还在冷档；本轮不顺带猜写他的近况。这里也没有理由改变钥匙的持有人。

```xml
<LoreState version="3" mode="delta">
  <Shared><时间>第四天中午</时间></Shared>
  <Entity id="E01" mode="delta" pending="false" presence="cold" confirmed="第四天中午">
    <当前状态>十本书已交付，订单完成</当前状态>
  </Entity>
</LoreState>
```

### 第六轮：这次没有状态变化

```xml
<LoreState version="3" mode="delta"></LoreState>
```

## 改成自己的题材

校园卡可以把事件换成“周五交还笔记”，物品换成“借出的笔记本”；经营卡可以换成“客户订单、仓库货物、供应商”。保留通用栏目与更新原则，再重写初始事实即可。

不要仅替换显示标题而忘记条目与 `data-lore-field`。栏目名需要三处一致：规则、HTML 绑定、模型输出的栏目标签。
