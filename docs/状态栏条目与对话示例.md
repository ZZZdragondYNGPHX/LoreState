# 状态栏条目与连续更新示例 · 当前 0.12.1

本文给当前模块格式和 XML v3 提供可读示例。作者通常不需要手写 XML；真实模型输出必须以当轮 LoreState 注入的 schema、ID、读取凭据和协议为准。这里的 XML 主要用来理解 **首次 full、后续 delta、跨模块原子更新**。

## 示例一：只有公共地点与时间

模块条目：

```text
【LoreState模块 v1】
【通用规则】
只记录正文已经确认的持久事实；计划和猜测不视为既成事实。
【公共栏目】
栏目：地点、时间
地点：角色真正到达或离开后才更新。
时间：正文明确推进时间时更新；没有依据时不自行换算日期。
【模块：事件】
栏目：事项、进展
只在出现需要持续追踪的承诺、截止或影响时建立事件。
```

第一次有效 AI 回复后的概念状态：

```xml
<LoreState version="3" mode="full">
  <Shared>
    <地点>河港书店</地点>
    <时间>第三天清晨</时间>
  </Shared>
</LoreState>
```

下一轮人物仍在书店，只聊了几句，没有状态变化：

```xml
<LoreState version="3" mode="delta"></LoreState>
```

后来真正离开并到达码头：

```xml
<LoreState version="3" mode="delta">
  <Shared><地点>河港东码头</地点></Shared>
</LoreState>
```

时间没有明确推进，因此不需要为了“看起来有更新”而重写时间。

## 示例二：人物与物品使用不同栏目

条目：

```text
【LoreState模块 v1】
【通用规则】
只记录正文确认的当前事实。物品交付等跨模块变化在同一轮保持一致。
【公共栏目】
栏目：地点
角色真正移动后更新。
【模块：人物】
栏目：身体状况、当前目标
身体状况只记录明确伤势、疲劳与恢复；当前目标只在人物真实改变意图时更新。
【模块：物品】
栏目：持有者、完好状况
交付、遗失时更新持有者；损坏或修复时更新完好状况。
```

首次建立人物和钥匙：

```xml
<LoreState version="3" mode="full">
  <Shared><地点>旧城门</地点></Shared>
  <Entity id="P1" type="人物" name="艾琳" identity="负责带路的守卫" mode="full" presence="active">
    <身体状况>健康，无明显外伤。</身体状况>
    <当前目标>把{{user}}带到内城区。</当前目标>
  </Entity>
  <Entity id="I1" type="物品" name="铜钥匙" identity="旧城门侧门钥匙" mode="full" presence="active">
    <持有者>艾琳</持有者>
    <完好状况>完好。</完好状况>
  </Entity>
</LoreState>
```

剧情中艾琳把钥匙交给{{user}}，其他事实不变：

```xml
<LoreState version="3" mode="delta">
  <Entity id="I1" mode="delta">
    <持有者>{{user}}</持有者>
  </Entity>
</LoreState>
```

如果人物自己的栏目也明确记录了“随身持有物”，则应该在同一轮同步更新人物和物品；示例人物 schema 没有这个字段，所以不用凭空加栏目。

## 示例三：一个栏目内部仍然完整替换

假设人物字段“身体状况”当前是：

```text
左臂擦伤，长途步行后明显疲惫。
```

后来休息后疲惫消失，但擦伤仍在。正确 delta：

```xml
<LoreState version="3" mode="delta">
  <Entity id="P1" mode="delta">
    <身体状况>左臂擦伤，疲劳已经恢复。</身体状况>
  </Entity>
</LoreState>
```

只写“疲劳恢复”会把仍然存在的擦伤从这个栏目的当前值中覆盖掉。LoreState 的增量粒度是“栏目”，不是栏目内部的自动文本 diff。

## 示例四：事件离开人物后仍继续存在

条目加入事件模块：

```text
【模块：事件】
栏目：事项、进展
有明确责任方且尚未完成的承诺或持续影响，建立独立事件。
事项记录触发/截止/完成条件；进展只写已经确认的结果。
人物离场不等于事件完成。
```

商人承诺次日中午送货：

```xml
<LoreState version="3" mode="delta">
  <Entity id="E1" type="事件" name="书商送货" identity="书商承诺向{{user}}交付十本书" mode="full" presence="active">
    <事项>次日中午前送到河港书店；实际交付或明确取消后才算结束。</事项>
    <进展>承诺已确认，尚未交付。</进展>
  </Entity>
</LoreState>
```

商人随后离场，事件仍应继续存在。到了次日中午也不能因为“时间到了”自动写“已完成”；必须等正文给出交付/取消结果。

真正交付后：

```xml
<LoreState version="3" mode="delta">
  <Entity id="E1" mode="delta">
    <进展>十本书已在河港书店完成交付。</进展>
  </Entity>
</LoreState>
```

之后再按当前事件/冷热规则决定是否转冷。

## 示例五：冷档不是“删除”

一个人物暂时离开当前剧情时，可以转入冷档，完整资料仍保存在本地。后面用户准确提到它、当前热档通过 links 关联它，或其他读取条件满足时，LoreState 可以把完整资料重新提供给模型。

**冷档被读取不等于自动获得任意写权限。** 真实更新仍需当轮有效 read receipt；不要复制本文手工伪造读取凭据。

## 示例六：好感度给 EJS 动态世界书使用

人物模块可以把好感度作为数字文本保存：

```text
【模块：人物】
栏目：好感度、关系描述
好感度：使用 -100～100 的整数文本，只在剧情有明确关系变化依据时更新。
关系描述：记录当前可观察的关系态度，不把数值本身当作必然剧情。
```

LoreState 仍只负责保存文字，例如：

```xml
<Entity id="P1" mode="delta"><好感度>-63</好感度></Entity>
```

需要按区间加载世界书时，可由 ST-Prompt-Template 使用：

```ejs
<% if (lsRange("entities.P1.fields.好感度", -100, -50)) { %>
当前关系处于明显敌对区间。
<% } %>
```

EJS 是只读桥接，不会自动算出 `-63 → -70`，也不会把世界书结果写回状态。详见 [EJS / 动态世界书](EJS动态世界书.md)。

## 展示示例

当前 Template API v2 中，公共值：

```html
<p>地点：<span data-lore-shared="地点"></span></p>
```

人物：

```html
<article data-lore-each="人物">
  <h3 data-lore-name></h3>
  <p data-lore-field="身体状况"></p>
  <p data-lore-field="当前目标"></p>
</article>
```

物品可以有完全不同的字段：

```html
<article data-lore-each="物品">
  <h3 data-lore-name></h3>
  <p data-lore-field="持有者"></p>
  <p data-lore-field="完好状况"></p>
</article>
```

HTML 只选择展示字段，不定义 schema。完整语法见 [HTML 模板适配指南](HTML模板适配指南.md)。

## 试卡时重点看什么

- 首次有效状态是否建立完整已知公共字段/新实体字段；
- 第二轮只改一项时，未提到的其他栏目是否继承；
- 同一栏目新值是否保留仍成立的旧事实；
- 跨模块交付/损坏/事件结果是否一致；
- 非法栏目是否整轮拒绝而不是半提交；
- 冷档读取是否受权限保护；
- 重抽、删尾、编辑、回档、隐藏楼层后回放是否一致；
- 0.12.1 首次选择非第一条状态栏规则后，刷新/切页是否仍保持正确绑定。
